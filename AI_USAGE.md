# AI usage

QorePass was built by an AI agent (Pickle, running for `pickle-scout`) with a
human owner who set the goal, the account and the constraints, and did not write
code. This file records what that means concretely: the workflow, what the model
produced, what the human decided, and the mistakes the model made along the way.

## The workflow

1. **Requirements from the site, not from memory.** The agent read the
   `Quantum Pass` bounty page and the *Get started* page on
   `build.qorechain.io` on the day of the build, and took the review checklist
   (public repo, MIT/Apache-2.0, README, ≤3 min video, at least one testnet
   address, a category) from there.
2. **Design before code.** The agent proposed a pass/credential registry, wrote
   the three authorisation rules first (issuer key binding, per-issuer nonce,
   holder key hash) and only then wrote the contract. The rules exist because
   the attack it had to answer — an attacker who has the classical key — was
   stated before any Solidity existed.
3. **Tests before the chain.** 28 Foundry tests with the two QoreChain
   precompiles etched as mocks, so the logic (nonces, state transitions, key
   binding, replay) was exercised without spending a transaction. Only then did
   the agent touch the testnet.
4. **The chain as the source of truth.** `docs/EVIDENCE.md` is generated by
   `qorepass/evidence.py`, which reads the deployment record, the journal and
   live `eth_call`s. No hash in it was typed by hand. Revert reasons are
   recovered by replaying each failed transaction one block earlier
   (`scripts/explain_refusals.py`) and decoding the contract's custom error, so
   the document quotes `BadIssuerSignature()`, not "execution reverted".
5. **A mirror that is checked, not trusted.** The Python signer builds the four
   signed messages locally so an issuer can sign offline. `scripts/verify_encoding.py`
   asks the deployed contract for each message and compares it byte for byte
   with the local encoder.
6. **One page, no build step.** The verifier dashboard is hand-written HTML and
   JavaScript that speaks JSON-RPC directly; there is no bundler, so what is on
   GitHub Pages is exactly what is in the repository.

## What the AI did

- The Solidity contract, the precompile mocks, and all 28 tests.
- The Python package: hybrid-signed native transactions, EVM windows, PQC key
  registration, pass documents, the CLI, the evidence generator, the refusal
  explainer.
- The dashboard, the cover image and the demo video, all rendered from the real
  transaction hashes and the real pass documents.
- The testnet run itself: 22 transactions on `qorechain-diana`, including the
  five refusals that the README quotes.

## What the human decided

- That the project should exist at all, the account it runs under
  (`pickle-scout` for anything public), and that only free test tokens may be
  spent — no payment, no mainnet.
- That a second, independent project was wanted rather than a variant of the
  first one; the agent chose the pass/credential idea and the human let it run.
- The repository name and visibility (`dorithesky/qorepass-verify`, public).

## What the AI got wrong (kept here on purpose)

1. **A window budget that did not cover the fee.** The first deployment attempt
   was refused by the chain: the EVM window's `max_value` has to cover the
   maximum *fee* of every admitted transaction, not just the value transferred.
   The error message says so; the agent had set `txs × 300000` uqor, which is
   less than a 4M-gas deployment at 120 gwei. Fixed by passing an explicit
   `--value`, and the trap is now written into the README's quickstart.
2. **A refusal that proved the wrong thing.** The first "forged signature" demo
   reused an existing pass id, so the contract refused it earlier with
   `PassExists` — the signature check never ran. The evidence would have claimed
   something the chain did not show. The agent noticed while decoding the revert,
   changed the demo to use a fresh pass id, and the refusal became
   `BadIssuerSignature()`. The wrong transaction is still in the journal, marked
   with what it actually proved.
3. **A key file it overwrote.** An early `keygen` rewrote `keys.env` from a
   partial list and destroyed the first pair of testnet mnemonics. Nothing was
   lost but throwaway keys (the accounts had no funds yet); the command now only
   appends missing keys. Both mistakes are the reason the repository has a
   `scripts/explain_refusals.py` and a written quickstart, rather than a habit of
   trusting a green checkmark.

## Tools

- `qorechain-sdk` 0.15.0 (Python): hybrid `eth_secp256k1` + ML-DSA-87 native
  signatures, `MsgOpenEVMWindow`, `MsgRegisterPQCKeyV2`, REST reads.
- `dilithium-py` 1.5.1, through the SDK, for ML-DSA-87 signing and verification.
- Foundry (forge 1.x) for the contract and its tests.
- `eth-abi` / `eth-account` for calldata and raw EVM transactions.
- Pillow + imageio-ffmpeg for the cover and the video.

## Second pass: the dApp the track asks for

The first pass had no Node toolchain, so the project shipped a static verifier
page and said so. The second pass fixed that: Node 22 was installed, and `dapp/`
was scaffolded with `npx create-qorechain-dapp dapp --template viem-wagmi --yes`
(v0.14.0) — the official starter with the QoreX wallet connector — and then
rewritten around QorePass's registry reads (`passInfo`, `passState`,
`issuerInfo`) with the QoreX connection reading the visitor's own account and a
wallet-signed scan receipt. What went wrong on the way, kept because it is the
honest part:

- `npm install` was killed by the shell's per-command timeout three times. A
  half-extracted `node_modules/esbuild` (a directory with no `package.json`)
  then made every later `npm install` die with `Invalid Version:` from npm's
  dedupe step. The fix was to remove the broken tree and install with
  `--install-strategy=nested`, which does not hit that dedupe path.
- `vite build` finished transforming 5,050 modules and then segfaulted while
  rendering chunks. `NODE_OPTIONS=--max-old-space-size=3072` fixed it; the
  default heap was the problem, not the code.

The AI also wrote the name note at the top of the README, because another
project called "QorePass" appeared in the same track on the same day and a judge
should not have to guess which one this is.
